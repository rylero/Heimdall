# Heimdall Architecture Review — 2026-07-06

Scope: architecture, structure, config, big-picture decisions. Implementation-detail review is a follow-up pass (see "Handoff" at bottom).

## 1. Architecture snapshot

- **Jetson side (C++20)**: DeepStream pipeline (2 USB cams → nvinfer YOLO/RF-DETR) → detection worker → `DetectionProcessor` (PoseBuffer lookup → ground projection → JPDAF/Kalman) → ZMQ PUB. Separate AprilTag thread (cam 3, V4L2 → tag36h11 → constrained PnP) → ZMQ PUB. Pose PULL from robot.
- **Robot side (Java vendordep)**: `HeimdallClient` daemon IO thread over 3 ZMQ sockets; helpers (`InterceptSolver`, `MotionPrediction`, `VelocityObstacleAvoider`).
- **Web UI (FastAPI + SQLite)**: config CRUD + raw detection SUB on 5556.
- **Offline**: recording + `heimdall_replay` (hardware-free `heimdall_core`), replay Docker image.

### What's good (keep)
- Library layering is genuinely clean: `heimdall_tracker` / `heimdall_pose` / `heimdall_comm` / `heimdall_core` build hardware-free; pipeline only builds when DeepStream present. Enables x86 dev + unit tests.
- `DetectionProcessor` shared between live app and replay — the replay/record loop is the strongest reliability asset in the repo.
- Protobuf-over-ZMQ with PUB (latest-value) semantics fits the "drop stale, never block" requirement; `dontwait` fix already applied.
- Dockerfile layer strategy (stub sources → dep build → source copy) gives fast rebuilds.
- Config as mounted jsonc files = tune without recompile.

## 2. Architecture issues (ranked)

### A. No clock synchronization between robot and Jetson — CRITICAL
Three related problems, one root cause:
1. `VisionPoseMsg.timestamp_ns` is Jetson `CLOCK_MONOTONIC` (`apriltag_detector.h:9`). Example robot code (`HeimdallIOReal.java`, deleted example) passes `vpe.getTimestampSecs()` toward `addVisionMeasurement()`, which expects **FPGA timebase**. Jetson monotonic seconds are unrelated to FPGA seconds → WPILib pose-buffer latency compensation is garbage-in. Either it silently degrades or the estimator rejects/mis-applies every vision measurement.
2. Robot's `sendPose` timestamp (`System.nanoTime()`, also wrong — should be FPGA time) is **ignored**: Jetson tags poses with reception time (`CommLayer::TimestampedPose.jetson_recv_ns`) and `PoseBuffer::closest()` matches frames by recv time. Network jitter + scheduling delay directly corrupt detection→pose association.
3. No modeling of camera capture latency (USB/UVC exposure→DMA can be 30–80 ms).

**Fix direction**: add a clock-offset estimation protocol — REQ/REP ping on a 4th socket, robot sends FPGA time, Jetson computes offset + RTT (simple NTP-style, filter with min-RTT samples). Then (a) stamp `VisionPoseMsg` in robot timebase, or better send **latency** (`now - capture_ns`) so robot computes `fpgaNow - latency`; (b) use robot timestamps for PoseBuffer matching. This is the single highest-value fix in the project.

### B. VisionPoseMsg carries no quality metadata — HIGH
Robot cannot set dynamic std devs for `addVisionMeasurement`. Add to proto: tag count, avg tag distance, reprojection error, ambiguity flag/solve mode (gyro-constrained vs IPPE fallback). Without this, a single distant ambiguous tag is trusted equal to a close multi-tag solve — classic FRC pose-jump failure.

### C. Config split-brain — HIGH
Web UI persists to its own SQLite (`web/app/database.py`); heimdall reads `config/*.jsonc` at startup only. Nothing bridges them. Also `config/cameras/` mixes `cam1.jsonc`/`cam2.jsonc` with `camera_0.json`/`camera_1.json` (two naming schemes, two formats).
**Fix**: one source of truth — files. Web UI reads/writes the jsonc files and signals heimdall (control socket or SIGHUP → hot-reload tracker params; restart for pipeline changes). Delete SQLite config tables or reduce DB to detection history only.

### D. No supervision / competition-hardening — HIGH
- `docker-compose.yml`: heimdall service has **no `restart:` policy** (mediamtx has one). Crash mid-match = vision gone until SSH.
- No host-side watchdog (systemd unit enabling `docker compose up -d` at boot), no boot-time budget measured.
- Camera identity by enumeration order; USB re-enumeration after brownout can swap cam0/cam1/AprilTag cam. Bind by `/dev/v4l/by-id/` or serial.
- `healthy` flag exists but no self-healing: pipeline stall detection (known failure mode per project history) should trigger internal pipeline restart, not just `healthy=false`.

### E. Time-source robustness of `healthy` on robot side — MEDIUM
`HeimdallClient.isHealthy()` uses wall-clock `System.currentTimeMillis()`; DS/NTP time jumps on the rio can flap health. Use `System.nanoTime()` deltas.

### F. Protocol/versioning — MEDIUM
- No version/magic field in any proto message; vendordep jar and Jetson image can silently skew. Add `uint32 proto_version` to each top-level message or a handshake.
- `HeimdallVendorDep.json` mavenUrl is `file:///C:/Users/ryan/...` — works only on this machine. Host maven repo + `jsonUrl` (GitHub Pages / releases) before anyone else uses it.

### G. Repo hygiene — MEDIUM
- Tracked build artifacts: `web/app/proto/__pycache__/*.pyc`, `vendordep/bin`+`build` outputs, `.gradle/`. Add to .gitignore + `git rm --cached`.
- `train/` vs `training/` — two overlapping Python training dirs, each with its own committed?/local `.venv`. Consolidate to one.
- Root-level strays: `pose_range.json`, `context-snapshot.{json,md}`, `session-log.md`, `logs/`, `recordings/`, `build/` in repo root — move to gitignored scratch or `docs/`.
- Working tree currently has uncommitted deletion of `examples/HeimdalTest/` and modified `detection_processor.*`, `comm_layer.cpp` — decide and commit; example project is referenced by README.

### H. Test strategy gaps — MEDIUM
Good: tracker/kalman/jpda/pose/comm/pose_buffer unit tests. Missing:
- No CI. `heimdall_core` + tests build on x86 — a GitHub Actions job is cheap and would catch regressions.
- No replay-based regression test (golden recording → expected track events). The infra exists; wire it into CTest.
- No tests for AprilTag solve math (constrained solve vs IPPE fallback) — highest-risk untested code.
- Vendordep tests cover solvers but not `HeimdallClient`/proto round-trip against C++ (a cross-language proto golden test is easy: canned bytes both sides).

### I. AprilTag subsystem is a second, parallel pipeline — LOW/ACCEPTED
V4L2+OpenCV thread outside DeepStream is pragmatic and fine at one camera. Note the constraint: scaling to 2+ tag cameras or GPU-accelerated detection (cuAprilTags) will want it folded into the main pipeline or a per-camera thread pool. Don't rework now; keep the interface (`detect() → VisionPoseResult`) stable so the backend can swap.

### J. Web UI value proposition unclear — LOW
Currently: SQLite CRUD + raw detection tail. Its real jobs at competition are (1) live camera preview w/ overlay, (2) health dashboard, (3) config edit + apply, (4) calibration wizard. Decide whether it's a config tool or an ops console; right now it's neither fully.

## 3. Roadmap — "most powerful FRC vision system"

Ordered; each unlocks the next.

1. **Time sync + timestamped, std-dev-weighted vision measurements** (fixes A+B). Everything downstream (auto-align, pose accuracy claims) depends on this.
2. **Replay regression suite + x86 CI** (H). Locks in tracker behavior before further tuning; protects against the freeze-bug class you've already hit three times.
3. **Competition hardening** (D): restart policy, systemd boot, by-id camera binding, pipeline stall auto-restart, boot-time measurement, match auto-recording with disk rotation (trigger recording off robot enabled-state via the pose stream).
4. **Multi-tag joint PnP**: solve all visible tags in one constrained solve against the field layout (MegaTag2-style) instead of per-tag; big accuracy + ambiguity win, pairs with B's quality metadata.
5. **Robot detection class**: add opponent-robot class to the detector; JPDAF already tracks, `VelocityObstacleAvoider` already consumes — this makes Heimdall a full dynamic-obstacle system, the differentiating feature vs Limelight/PhotonVision.
6. **Multiple AprilTag cameras** + per-camera extrinsics in one layout config (I).
7. **NT4 mirror channel**: publish tracks/pose/health to NetworkTables for AdvantageScope/dashboards while keeping ZMQ as the control path — solves observability without sacrificing latency.
8. **Calibration UX in web UI**: intrinsics wizard (charuco), extrinsics-from-tag, quality report; today calibration is scattered Python tools.
9. **Vendordep distribution** (F): hosted maven + jsonUrl, versioned releases matched to Docker image tags.
10. **Game-piece 3D / airborne handling**: current ground-plane projection assumption breaks on held or launched pieces; add height-aware projection per class or ignore-when-held logic.
11. **Model lifecycle**: consolidate `train/`+`training/`, dataset versioning, one-command retrain→TRT-engine→deploy path (web UI model_mgmt router hints at this — finish it).

### HIGH

**5.1 — Detection queue drops the NEWEST frame under load** · `src/app/heimdall_app.cpp:47`
`enqueue_detections()` does `if (size >= kMaxDetQueue) return;` — tail-drop. When the det worker
(`processor_.process`) falls behind (heavy JPDAF frame, snapshot write, log flush), the queue fills and
**every fresh frame is discarded while the worker chews stale backlog**. Latency grows without bound until
the worker catches up; the tracker consumes camera state that is up to 8 frames old. This is the exact
opposite of the "drop stale, never block" invariant the ZMQ PUB layer is built around.
*Failure:* momentary worker stall (e.g. snapshot request) → robot acts on 130 ms-old track positions
mid-match, then a latency spike that never recovers until detections briefly stop.
*Fix:* drop the OLDEST instead — `det_queue_.pop()` before `push()` when full (or make it a size-1
latest-value slot, since `process()` already handles multi-detection frames atomically). Keep newest.

**5.2 — JPDAF update omits the spread-of-innovations covariance term** · `src/tracker/jpda.cpp:76-90`, `src/tracker/kalman.cpp` (all `kalman_update_*`)
The update applies a single weighted innovation with `total_beta` and reduces `P` by `β·K·H·P`
(`kalman.cpp:46/112/199`). Proper JPDAF adds the moment-spread term
`K·[Σ βⱼ νⱼνⱼᵀ − ν̄ν̄ᵀ]·Kᵀ`, which *inflates* covariance when a track is torn between multiple gated
detections. Omitting it makes the filter **overconfident precisely when association is ambiguous** — P
shrinks toward zero, gain collapses, the track stops responding to measurements and locks onto whichever
blob it drifted toward. This is the mechanism behind the "P decaying to zero on long tracks" freeze in the
bug history; `pos_cov_floor` (`kalman.cpp:15/81/168`) is a band-aid that clamps the symptom on the x/y
diagonal only.
*Failure:* two game pieces cross / merge in the detector → both tracks' P collapse → tracker reports a
frozen, confident-but-wrong position after they separate.
*Fix:* add the spread term to each `kalman_update_*`, or (cheaper, principled) scale the effective
measurement-noise R up by `1/total_beta` before the update so ambiguous frames widen the posterior. Then
revisit whether `pos_cov_floor` is still needed.

**5.3 — Robot→Jetson pose send is throttled behind the 5 ms detection recv** · `vendordep/.../HeimdallClient.java:181-192`
The single IO thread sends the pending pose (step 1), then **blocks up to 5 ms** on `trackSub.recv(0)`
(`setReceiveTimeOut(5)`, line 173) before looping back to send the next pose. A pose handed to
`pendingPose` right after a recv starts waits the full poll timeout before it leaves the socket → up to
~5 ms of added, variable latency on every pose, on top of the network hop. Combined with §2A (wrong
timebase) and §5.7, this directly corrupts detection↔pose association.
*Failure:* fast rotation/translation during auto → pose timestamps lag reality by a jittering 0–5 ms →
ground projection and gyro-constrained AprilTag solve smear.
*Fix:* don't gate the send path on the detection recv. Use a `ZMQ.Poller` over both sub sockets (send pose
unconditionally each wake), or move the PUSH send to its own thread triggered on `sendPose()`.

### MEDIUM

**5.4 — No CONFLATE / HWM on any PUB or SUB socket** · `src/comm/comm_layer.cpp:13,16`; `HeimdallClient.java:168-179`
Sockets use default `SNDHWM/RCVHWM=1000`, no `ZMQ_CONFLATE`. `dontwait` prevents blocking, but a briefly
slow subscriber accumulates up to 1000 queued frames and then reads **stale backlog**, not the latest
value — defeating the latest-value design. §2A/§2D depend on this being correct.
*Fix:* set `ZMQ_CONFLATE=1` on the tracks PUB, apriltag PUB, and the robot-side subs (must be set *before*
bind/connect). Pose PULL can keep a small RCVHWM. Verify conflate interaction with multipart if topics are
ever added.

**5.5 — V4L2 capture timestamp assumed monotonic & non-zero, never validated** · `src/apriltag/apriltag_detector.cpp:453-455,495`
`capture_ns` is taken raw from `buf.timestamp` and fed to `interpolate_yaw()`. Not all UVC drivers set
`V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC`; some emit 0 or a start-of-exposure clock. If `capture_ns` is 0 (or
any value older than the gyro history), `interpolate_yaw` hits the `it == begin` branch
(`apriltag_detector.cpp:278`) and **back-extrapolates yaw over a multi-second negative dt → garbage
heading**, which then drives `constrained_pnp`. Silent wrong pose, not a rejection.
*Fix:* check `buf.flags & V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC` at STREAMON; if absent, fall back to
`clock_gettime(CLOCK_MONOTONIC)` at DQBUF. Reject/clamp `capture_ns` older than the oldest gyro sample.

**5.6 — AprilTag object-point order vs. library corner order unverified** · `src/apriltag/apriltag_detector.cpp:487-492` vs `d->p[]` at `:532`
`obj_pts` is hand-listed starting top-left (`{-hs,hs},{hs,hs},{hs,-hs},{-hs,-hs}`) and paired index-for-index
with apriltag's `d->p[]`, whose documented order is bottom-left→bottom-right→top-right→top-left in image
space (y-down). If these don't line up, IPPE_SQUARE and the constrained solve both still return a
low-reprojection solution — but **rotated/mirrored** — so the error is invisible in reproj error and only
shows as a consistently wrong field pose.
*Failure:* AprilTag pose is reflected/rotated 90–180° from truth; looks "locked and confident."
*Fix:* verify against a known tag at a measured position (mock or single static frame). Cross-check corner
order against PhotonVision/wpical's ordering, which is the reference for this exact solve.

**5.7 — Gyro sample stamped at Jetson receive time, not measurement time** · `src/app/heimdall_app.cpp:72-76`
`update_gyro(..., p->jetson_recv_ns)` labels the yaw with when the Jetson *received* the pose, but
`interpolate_yaw` treats it as when the yaw was *true*. The network+poll latency (§5.3) shifts every gyro
sample later in time than reality, biasing the interpolated yaw at capture during rotation. Impl-level facet
of §2A; note it here because the fix (send capture-relative latency / robot timebase) lands in this call.

**5.8 — AprilTag thread can hang shutdown on a blocking DQBUF** · `src/app/heimdall_app.cpp:83-94`, join at `:113`
`apriltag_loop` calls the blocking `detect()` (VIDIOC_DQBUF, no O_NONBLOCK); `running_` is only checked
between frames. If the tag camera stalls (brownout, USB re-enumeration — a known failure mode, §2D),
`detect()` blocks forever and `at_thread_.join()` deadlocks `stop()`.
*Fix:* open the fd `O_NONBLOCK` and `poll()` with a timeout in `detect()`, or `select()` on `v4l2_fd` with
a `running_` check; return `nullopt` on timeout.

**5.9 — Velocity/acceleration covariance is never floored; only x/y are** · `src/tracker/kalman.cpp:15-16,81-82,168-169`
`pos_cov_floor` clamps `P[0][0]`,`P[1][1]` only. For CV/CA models the velocity/accel variances
(`P[2][2]…P[5][5]`) can be driven down by repeated updates with no floor. On long-lived tracks this lets the
velocity estimate ossify, so a suddenly-maneuvering object is tracked with a stiff, stale velocity until the
miss-streak drops it. Secondary contributor to the freeze class in the bug history.
*Fix:* prefer fixing §5.2 (proper covariance growth removes the need to clamp). If keeping the floor,
extend it to the velocity (and accel) diagonal, or enforce a minimum via the process-noise Q instead.

### LOW

**5.10 — `gate_distance` config comment is wrong; the real Mahalanobis gate is unconfigurable** · `config/heimdall.jsonc:16-18`, `src/tracker/jpda.cpp:55,58`
Comment calls it the "Mahalanobis gate distance … (meters)". Code uses it as a plain **Euclidean** pre-gate
(`sqrt(dx²+dy²) >= gate_distance`, line 55); the actual Mahalanobis/chi-square gate is a hardcoded
`MAHALANOBIS_GATE_THRESHOLD` (line 58) with no config knob. Misleading when tuning; you cannot adjust the
statistical gate without a recompile.
*Fix:* correct the comment ("Euclidean pre-gate, meters"); expose the Mahalanobis threshold in `JpdaConfig`.

**5.11 — IPPE ambiguity=0 when the second solution is near-perfect** · `src/apriltag/apriltag_detector.cpp:389`
`ambiguity = (n>=2 && errors[1]>1e-6) ? errors[0]/errors[1] : 0.0`. When `errors[1] ≈ 0` both solutions
reproject perfectly — the *maximally* ambiguous case — yet the guard sets ambiguity to 0 and blindly picks
solution 0, skipping floor disambiguation. Rare (needs a near-degenerate view) but backwards.
*Fix:* treat `errors[1] < ε` as ambiguity ≈ 1 (force disambiguation), not 0.

**5.12 — `interpolate_yaw` "interpolate" branch extrapolates, ignores the bracketing sample** · `src/apriltag/apriltag_detector.cpp:285-289`
Comment says "Interpolate between prev and it," but the code returns `prev->yaw + prev->vyaw*dt` — velocity
extrapolation off `prev`, never reading `it->yaw`. Mislabeled and uses a possibly-stale `vyaw` instead of
the true slope between the two straddling samples.
*Fix:* linear-interpolate: `lerp(prev->yaw, it->yaw, (target−prev.ts)/(it.ts−prev.ts))`, handling angle wrap.

**5.13 — Empty-frame timestamp blends pipeline PTS with wall-clock elapsed** · `src/app/detection_processor.cpp:36-43`
On empty frames `ts_s = last_timestamp_ns_·1e-9 + wall_elapsed_s` mixes the pipeline buffer PTS timebase
with `steady_clock` elapsed. Benign today (only used to advance `frames_missed`, and `kalman_predict` guards
`dt>0`), but if the two clocks diverge the miss-timeout drifts. Documented here so it isn't "fixed" into a
regression later.
*Fix:* carry the pipeline's own clock for the empty-frame dt, or accept and comment the approximation
explicitly.

### Notes / no-defect confirmations
- Ground-plane projection math (`pose_estimator.cpp`) checks out: unproject→robot→field rotation, downward-ray
  test, ground intersection all correct. Iterative undistort (`:20-28`) updates `v` using the just-updated
  `u` within an iteration — negligible numerically, converges.
- `constrained_pnp` linear system (`apriltag_detector.cpp:330-355`) is algebraically correct
  (verified the `[fx,0,cx−u]·t = (u−cx)Qz − fx·Qx` derivation and the `T_field_tag·inv(T_cam_tag)·inv(T_robot_cam)`
  transform chain).
- `total_beta < 1` always (`jpda.cpp:69-72`), so the covariance update cannot over-subtract from the weight —
  the freeze risk is §5.2's missing term, not a negative-variance blow-up.
- `steady_clock` (comm recv) == `CLOCK_MONOTONIC` (V4L2) on Linux/libstdc++, so the *AprilTag* gyro/capture
  matching shares one domain. **But the DeepStream detection path does NOT — see 5.14.** The robot-side FPGA
  break (§2A) is separate again.

### Second pass — pipeline, tracker lifecycle, replay, plumbing, vendordep

Covers everything except the web app (per request): `pipeline/*`, `tracker.cpp`, `probe.cpp`,
`camera_source.cpp`, app plumbing (`recording/replay/output/snapshot`), config loaders, and the full

#### HIGH

**5.14 — Detection `capture_monotonic_ns` is GStreamer running-time, not CLOCK_MONOTONIC → PoseBuffer matching is degenerate** · `src/pipeline/probe.cpp:80,86-87,125-126`
`base_time` is hardcoded `0`, so `capture_monotonic_ns = frame->buf_pts + 0`. `buf_pts` is the buffer's
**running-time** (nanoseconds since the pipeline hit PLAYING — small, starts at ~0). But `PoseBuffer::closest()`
matches this against `TimestampedPose.jetson_recv_ns`, which is `steady_clock::now().time_since_epoch()`
(`comm_layer.cpp:30`) — **absolute CLOCK_MONOTONIC (nanoseconds since boot — ~10¹³)**. The two values differ
by the entire machine uptime, so `|recv_ns − capture_ns|` is dominated by that constant and
`closest()` **always returns whichever pose has the smallest `recv_ns` — i.e. the oldest pose in the ring
buffer**, every frame. Detection→pose association doesn't just jitter (§2A.2); it is structurally broken: the
projected field position of every detection uses a stale, essentially fixed robot pose.
*Failure:* robot drives across the field; every game-piece detection is ground-projected through a pose from
~1 s ago (oldest buffer slot) → field positions smear by meters → tracker chases ghosts.
*Contrast:* the AprilTag path is fine — it matches V4L2 `buf.timestamp` (real CLOCK_MONOTONIC) against the
same-domain gyro `jetson_recv_ns`. Only the DeepStream path mixes clocks.
*Fix:* convert `buf_pts` to the absolute monotonic domain: `capture_ns = gst_element_get_base_time(pipeline)
+ buf_pts` (GstSystemClock is monotonic ≈ steady_clock), or — simpler and good enough — stamp each detection
with `steady_clock::now()` at the probe (loses only the intra-pipeline latency, keeps the domain correct).
This likely supersedes the §2A.2 fix priority: association is broken *today*, before any FPGA work.

#### MEDIUM

**5.15 — `queue_post_infer` is not leaky → a stalled encoder/RTMP backpressures and stalls nvinfer** · `src/pipeline/pipeline.cpp:169-176`
Every other queue in the graph is `leaky=2` (the tee branches, `:56`), but the post-infer queue is a plain
4-buffer queue. If `rtmpsink`/MediaMTX stalls (restart, network hiccup) the encode chain backpressures →
`queue_post_infer` fills → backpressure reaches `nvinfer` → **inference stops → `detection_probe_cb` stops
firing → no detections**. This is a concrete instance of the pipeline-stall failure mode in the bug history
and §2D. The detection probe sits at `infer_src` (before this queue), so detections are safe *only* as long
as infer keeps running — which this queue can prevent.
*Fix:* set `leaky=2` (GST_QUEUE_LEAK_DOWNSTREAM) on `queue_post_infer` so the display/encode branch can never
stall the detection path.

**5.16 — No pipeline stall detection; bus error kills the loop with no restart and no health signal** · `src/pipeline/pipeline.cpp:265-282`, `probe.cpp` (no watchdog)
`bus_cb` handles only ERROR/EOS, both of which just `g_main_loop_quit` → `run()` returns → vision is dead
until a human restarts. There is no detection of the silent-stall case (camera stops delivering buffers, no
error posted), and `healthy` is hardcoded `true` at every `send_tracking_frame` call
(`comm_layer.cpp` / `detection_processor.cpp:63,91,120`), so the robot's `isHealthy()` can't see a stall
either. §2D/roadmap-3, but flagged here because the code makes the false-confidence concrete: the health bit
exists end-to-end and is wired to a constant.
*Fix:* add a watchdog thread comparing `s_frame_count`/last-probe-time against a timeout; on stall, set an
atomic `healthy=false` (plumb it into `send_tracking_frame`) and trigger an internal pipeline
`NULL→PLAYING` restart. At minimum, stop hardcoding `healthy`.

**5.17 — Replay is not faithful: all poses preloaded + frames processed untimed** · `src/app/replay_main.cpp:56-62`; `src/app/recording.cpp:31-49`
Two issues that undermine the replay-as-regression-harness value (§2H, roadmap-2):
(a) All recorded poses are pushed into the buffer *before* any frame is processed (`:57-58`), so every
replayed frame can "see" poses that in live operation arrived *after* it — live causality is not reproduced
(compounded by 5.14, which makes the selection meaningless either way).
(b) Frames are replayed back-to-back with no inter-frame delay; empty frames derive `dt` from wall-clock
elapsed (`detection_processor.cpp:36-41`), which in a tight replay loop is ~0, not the real frame interval.
And `recording.cpp` stores timestamps **only per-detection** — an empty frame (`dets:[]`) records no
timestamp at all, so its timing can't be reconstructed. **Empty-frame LOST timing is therefore
non-deterministic between live and replay**, exactly the freeze/miss-timeout behavior the harness most needs
to lock down.
*Fix:* record a frame-level timestamp on every frame (incl. empty). In replay, drive `process()` off the
recorded timestamps (feed real `dt`), and either replay poses interleaved in recorded order or document that
replay is acausal-by-design.

**5.18 — `VelocityObstacleAvoider` full-stop fallback is returned without being verified safe** · `vendordep/.../VelocityObstacleAvoider.java:81-83,107-108`
When no sampled candidate is collision-free, the method returns `(0,0)` and comments it as "the safe
default." A full stop is **not** provably safe: against a moving obstacle heading at a stationary robot,
`(0,0)` still collides — the robot could have dodged. `(0,0)` is also never run through `isSafeAgainstAll`,
and never sampled as a candidate (speeds start at `maxSpeed/5`).
*Failure:* opponent robot / thrown game piece bearing down; avoider finds no safe sampled velocity, commands
a stop, robot gets hit while sitting still.
*Fix:* evaluate `(0,0)` explicitly; if even stopping is unsafe, fall back to the candidate that *maximizes*
closest-approach distance (least-bad), not a blind stop. Consider sampling `speed=0` and finer angles.

**5.19 — Tracker spawns a new track only for fully-unassociated detections → merged objects lose a track** · `src/tracker/tracker.cpp:41-45`, `src/tracker/jpda.cpp:101-108`
`jpda_update` returns a detection as "unassociated" only when *no* track gated it (`total_L == 0`). So if two
real objects fall within one existing track's gate, both are "associated," neither spawns a new track, and
**the second object is never tracked until the two separate beyond the gate distance**. Compounds 5.2 (the
surviving track's covariance also collapses between them).
*Fix:* spawn candidates from detections whose *best* β to any track is below a threshold (claimed-but-weak),
not only from totally-ungated ones; or run a one-to-one assignment pass for confirmed tracks first.

#### LOW

**5.20 — `ProtoReader` allocates an unbounded buffer from an untrusted length prefix** · `vendordep/.../proto/ProtoReader.java:85-87,124-126`
`int len = (int) readVarint(buf); byte[] embedded = new byte[len];` with no check that `len <= buf.remaining()`.
A corrupt/truncated frame can request up to ~2 GB before the subsequent `buf.get` throws (and is caught in
`ioLoop`). Trusted robot network, so low — but a mid-match bit-flip could spike memory / GC.
*Fix:* `if (len < 0 || len > buf.remaining()) throw ...;` before allocating. (Also: known-field branches
ignore `wireType` and assume the expected type; fine for a version-locked pair, worth a guard if you add
`proto_version` per §2F.)

**5.21 — USB source hardcodes `image/jpeg` + `io-mode=2`, no config knob** · `src/pipeline/camera_source.cpp:16-26`
Forces MJPEG and MMAP for every USB camera. Cameras that only offer YUYV, or that misbehave on MMAP and need
`io-mode=4` (userptr/RW), can't be accommodated without a recompile — and io-mode is the exact area flagged as
churny/fragile in the bug history. In the `!hw_decode` branch, `nvvidconv` also has no output caps, so its
handoff to `nvstreammux` (which wants NVMM) relies on implicit negotiation.
*Fix:* expose `pixel_format` and `io_mode` per camera in the camera config; add explicit
`video/x-raw(memory:NVMM)` caps after `nvvidconv`.

**5.22 — `s_cam_slots[8]` / decode-slot arrays assume ≤8 cameras; tiler assumes uniform resolution** · `src/pipeline/pipeline.cpp:8,145-150,186-187`; `probe.cpp:10`
`gst_pad_add_probe(sink, …, &s_cam_slots[i], …)` for `i` up to `cameras_.size()` with no bound check against
the fixed-size-8 arrays → out-of-bounds `user_data` if >8 cameras are ever configured. Tiler width/height use
`cameras_[0].width * cols` assuming every camera is the same resolution.
*Fix:* assert `cameras_.size() <= 8` at build (or size the arrays dynamically); compute tiler dims from the
actual max camera dimensions.

- `InterceptSolver` quadratic is correct across all regimes (target slower/faster/parallel-speed): with `c≥0`

- `ProtoWriter`/`ProtoReader` field numbers and wire types match `proto/heimdall.proto` exactly; proto3

- `HeimdallClient` mailbox design is sound: lock-free `AtomicReference` mailboxes, `getLatestVisionPose()`

## 6. Extended roadmap — additions beyond §3

From follow-up design discussion (2026-07-06). Three groups: perception add-ons, vendordep path planning, and the AdvantageKit dual-log replay system.

### 6.1 Perception / Jetson add-ons

- **Auto-exposure/gain controller** — per-camera feedback loop targeting tag/detection contrast rather than scene brightness. Venue lighting is the #1 practical failure mode at events.
- **Tag-on-robot detection** — detect opponent bumpers/numbers and fuse with object tracks so tracks carry team identity; enables defense-aware autos.
- **Sliding-window pose smoother on the Jetson** — small factor-graph over tag observations + received odometry (:5555 stream already exists); ship fused pose + covariance instead of raw per-frame solves. Moves beyond Limelight-equivalent.
- **`HealthMsg` self-diagnosis stream** — per-camera FPS, inference latency, drop counts, tracker load; lets robot degrade gracefully (e.g. disable auto-align) instead of relying on the binary `healthy` flag.
- **Zero-pose bootstrap** — if the robot never sends pose (crash, wrong IP), `PoseBuffer::closest()` returns a zero-initialized pose and object tracks silently project garbage (`pose_buffer.h:27`). AprilTag path should run standalone; object tracks should fall back to robot-relative coordinates with an explicit flag.
- **Venue auto-tuning** — record ~30 s at each venue, replay through `heimdall_replay` with a parameter sweep, pick gate/noise params per venue. The replay infra is the competitive moat; this weaponizes it.

### 6.2 Vendordep path planning

Primitives exist (`InterceptSolver`, `MotionPrediction`, `VelocityObstacleAvoider`); nothing composes them. Priority order **1 → 3 → 2**; all gated on latency-correct tracks (§2A — 100 ms stale at 4 m/s = 40 cm error; avoidance oscillates, intercepts miss).

1. **PathPlanner/Choreo obstacle shim** — expose tracked robots as dynamic obstacles to PathPlanner's on-the-fly replanning API (`Supplier<List<Pair<Translation2d, Translation2d>>>`). ~One class; every existing auto gains live opponent avoidance.
2. **Intercept-to-trajectory** — wrap `InterceptSolver` output into a holonomic trajectory re-solved each cycle: `HeimdallCommands.interceptPiece(drive, classId)` as a single Command. The showpiece feature.
3. **VO drive filter** — `ChassisSpeeds filter(ChassisSpeeds desired)` decorator around `VelocityObstacleAvoider` inserted before `runVelocity()`; teleop assist with zero driver-habit change. Also carries keep-out-zone clamping (penalty avoidance).
4. **Predictive pickup pose** — `MotionPrediction` + intake geometry: solve the pose where piece meets intake mouth at intake speed. Needs per-class friction/decel constants, measured from tracker logs.
5. **Time-parameterized occupancy (long-term)** — publish tracks as position + velocity + covariance ellipse over a horizon; local planner plans through *predicted* free space. Research-grade; only after 1–3 are competition-proven.

### 6.3 AdvantageKit dual-log replay ("fully replayed vision tuning")

Goal: record raw detections + inputs as a second log; replay robot code AND the vision pipeline together offline. Feasible in three tiers; **all gated on clock sync (§2A)** — merged logs need a common FPGA timebase.

- **Tier 1 — merged viewing**: replace the jsonl recording with a **wpilog writer** in `heimdall_core` (vendor wpiutil's standalone DataLog writer; no NT dependency). Log raw detections, received poses, AprilTag corners, tracker internals. AdvantageScope opens robot + Jetson logs merged on one timeline. Cheapest, transforms debugging. Add AprilTag raw corners to the recording — required to re-tune PnP offline (confirm `recording.cpp` coverage).
- **Tier 2 — patched replay**: re-run `heimdall_replay` with new params → Python tool rewrites the robot wpilog's `HeimdallIO` input entries with regenerated outputs → AdvantageKit replays robot code against the patched log. Scriptable: parameter sweep → N patched logs → N replays → scored. This is automated venue tuning end-to-end.
- **Tier 3 — native tracker in replay**: build `heimdall_core` for desktop, JNI-wrap it, log raw detection protobuf `byte[]` as AdvantageKit inputs; in replay mode the actual C++ tracker re-processes them with any config. `./gradlew replayWatch` + edit `heimdall.jsonc` = live tuning loop, zero reimplementation drift. Cost: JNI build matrix + shipping raw detections to the RIO for logging (few hundred bytes/frame).

Limitation: AdvantageKit replay is open-loop w.r.t. physics — you see what the code *would have commanded*, not where the robot would have ended up. Closing the loop = Tier 3 + maple-sim (replay-informed sim). ~90% of tuning value (tracker stability, pose rejection, std devs, intercept quality) lives in the open-loop tiers.

Sequence: **clock sync → Tier 1 → Tier 2 → Tier 3 if the workflow proves out.** Tiers 1+2 reuse `heimdall_replay` as-is and would make this the only FRC vision system with full-pipeline offline tuning.

### 6.4 Revised master ordering

Merging §3 and §6: time sync + std devs (§3.1) → replay regression + CI (§3.2) → **wpilog recording, Tier 1 (§6.3)** → competition hardening (§3.3) → PathPlanner obstacle shim + VO filter (§6.2.1/3) → multi-tag PnP (§3.4) → robot detection class (§3.5) → Tier 2 replay tuning → intercept command (§6.2.2) → the rest as demand dictates.
